
Two runs in separate fresh directories produced identical output. The capture includes standard output, standard error, exit codes, and the contents of saved JSON reports.

## Journeys

### Adopt a production gate and waive one exception

The user wants `python --ignore-tests` to report production findings, skip tests, and honor an intentional suppression. The source tree contains a production `TODO`, a suppressed `TODO`, a test `TODO`, and a malformed file.

The ordinary scan reported the production finding and the processing error, then exited 1. The strict variation with `--ignore-errors-on-exit` showed the suppressed finding and exited 2. After fixing the malformed file, a scan without `--ignore-tests` also reported the test finding. After removing the production `TODO`, the production scan exited 0. The strict scan still showed the retained suppression and exited 2. The saved JSON report after removal contained no findings or errors.

### Tune a team policy

The user wants to exclude the development marker rule and set a variable-name limit. The XML policy extends `python`, excludes `DevelopmentCodeFragment`, and sets `LongVariable` to 12 characters. The scan reported `customer_identifier` but not either marker. The malformed file remained a processing error, while `--ignore-errors-on-exit` left the finding exit code at 2. Raising the limit to 30 after the syntax correction produced a clean scan with exit 0. The modified policy persisted in the scratch tree until teardown.

### Save and correct a CI report

The user wants a JSON report that preserves findings and processing errors, and wants to repair invalid inputs without losing an existing report. An invalid ruleset exited 1 and left a sentinel report unchanged. With a valid policy, the command replaced the report even though the malformed source caused exit 1. The saved JSON contained the production finding and a separate `ProcessingError`. After correcting the syntax, the next report retained the finding, removed the error, and the command exited 2. After removing the finding, the next saved report had empty findings and errors and the command exited 0.

## Findings and limits

No confirmed bugs or unresolved candidates arose in these journeys. No new issue was filed. The tracker and existing closed reports were checked before the pass; the related processing-error and report-order fixes are [#258](https://github.com/quality-gates/messpy/issues/258) and [#277](https://github.com/quality-gates/messpy/issues/277).

The pass did not upload a report to a CI host, test Homebrew, or run other Python versions. The host had Python 3.14 but no `uv` installation. The project's lockfile-based setup could not be reproduced because the repository does not track a Python lockfile. The observed behavior is limited to the installed build and fixtures above.

The error for the invalid policy appeared on standard error and preserved the previous report. This makes it possible to distinguish an invalid policy from a valid report containing source errors. No usability issue was identified in the selected paths.
